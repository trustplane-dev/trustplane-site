The problem

A long-lived token is standing authority. Hand one to an autonomous agent and a single leak, or one prompt injection, authorizes every call it can reach.

Presented, not proven

API keys and bearer tokens grant access by mere possession. Whoever holds the string is the client, from anywhere, until it's rotated.

Not bound to the request

A token that may read /orders can be replayed against /admin the moment anything slips. The credential authorizes the actor, never the action.

Invisible after the fact

Keys leak into code, logs, and prompts. Without per-request proof there is no way to tell a legitimate call from a hijacked one.

"A token authorizes whoever is holding it. A proof authorizes one specific call. For software that runs on its own, that difference is the whole game."
How it works

Prove the request. Don't present a secret.

TrustPlane turns a workload's existing identity into a short-lived, request-bound credential that's verified locally, with no phone-home.

From the team

Why we built this

Secrets were never meant to be handed to software that acts on its own. An API key is a password that never sleeps: whoever holds it is you, from anywhere, until someone notices. That was a manageable risk back when a person pasted a key into a config file once a quarter.

It stops being manageable when an autonomous agent is making thousands of calls an hour and can be talked into making the wrong one. We didn't want to build another secrets manager, or another gateway with a longer config file. We wanted the request itself to carry proof, so the boundary can decide whether each exact call is allowed, every time.

That's the whole idea. Most of what's on this site is the plumbing that makes it practical.

— The TrustPlane team
