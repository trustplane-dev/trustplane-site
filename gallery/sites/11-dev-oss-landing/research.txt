Open-Source Auth Landing-Page Research for
trustplane.dev
Executive summary
The strongest open-source auth and identity landing pages share a narrow set of traits. They explain the
problem in one sentence, expose Get started , Docs , and Source/GitHub  immediately, show a realistic
install or integration path within the first screen or just below it, and use community/governance signals
instead of sales-heavy proof. Dex, SPIFFE/SPIRE, Authelia, Tinyauth, Kanidm, and Keycloak are the clearest
examples of this pattern. Their public pages foreground standards, installability, docs, and community
access over pricing, lead capture, or enterprise forms. 
By contrast, several modern auth products mix excellent developer UX with more commercial framing.
Authentik, Logto, ZITADEL, Hanko, and Ory product pages are useful references for feature packaging and
strong calls to action, but they also bring in “replace X,” pricing, cloud, compliance, or “contact us” language
earlier than a pure OSS homepage usually should. For a minimal, pure open-source  trustplane.dev, those
sites are better as secondary  inspiration than as the primary model. 
A practical direction for trustplane.dev is therefore: docs-first navigation, one primary CTA, one GitHub
CTA, no sales CTA above the fold, immediate install/quickstart proof, explicit license/repo visibility,
and community/security links in the header or footer . The overall aesthetic should feel closer to Dex +
Tinyauth + Authelia than to a SaaS homepage. 
One important limitation: in this pass, I could review public materials for Trustplane  and Clawvisor , but I
could not verify a clearly published OSS repo/license from the public landing materials I found. I therefore
treated them as adjacent references , not as confirmed OSS exemplars for the main comparison catalog.
Trustplane’s public docs emphasize machine identity, request proofs, short-lived JWTs, and audit; Clawvisor’s
public site emphasizes human-in-the-loop task approvals, credential vaulting, and policy enforcement for AI
agents.

more it drifts toward SaaS posture even if the software itself is open source. 14

The pattern to borrow is not “make the page look old” or “make it sparse for its own sake.” It is: make the
page decisively useful before it becomes persuasive . That means the visitor can answer , in under 10
seconds, what the project is, why it exists, how to try it, where the docs are, where the source is, and where
to ask for help. Dex and Tinyauth are especially strong at that. 
Trustplane.dev design system
Direction
For trustplane.dev, the best-fit direction is security-tool minimalism : serious, technical, standards-friendly,
and opinionated, but not cold. The page should feel like a public project homepage maintained by
engineers, not a funnel page maintained by demand generation. Use a single strong statement of purpose,
one primary CTA, one GitHub CTA, and put the quickstart or install proof immediately below the hero. That
direction is most aligned with Dex, Authelia, Tinyauth, Kanidm, and SPIFFE/SPIRE. 
A practical warning: if trustplane.dev is meant to communicate pure open source , do not use that phrase
unless the public repo and license are visible on launch day. Several successful OSS projects make the
license visible or obvious from the homepage or repo surface; that materially improves trust. 
Recommended style system
Area Recommendation
ToneCalm, direct, technical, audit-friendly. Avoid “revolutionize,” “enterprise-grade,” “AI-
powered platform,” and comparison-page chest-thumping on the homepage.
TypographyInter or IBM Plex Sans  for UI/body; JetBrains Mono  for code and badges.
Use 2 weights in body UI, 1 mono weight for snippets.
Page width 1200–1280px content max; keep hero copy narrow at ~10–12 words per line average.14

Sample homepage copy
The sample copy below is intentionally written in a pure OSS  voice. Where it echoes Trustplane’s public
concepts such as machine identity, short-lived credentials, and evidence-grade audit, it does so by adapting
wording from the public Trustplane docs rather than asserting a finalized public marketing position. 
Hero
Open-source trust for APIs and machine identity
Verify who is calling what, replace long-lived shared secrets with short-lived credentials, and
keep an evidence-grade audit trail for every critical action.
Get started  · View on GitHub
Feature cards
Prove every request
Bind identity and authorization to the request itself, not just to a static key.
Keep credentials short-lived
Issue scoped, temporary credentials after verification instead of passing around long-lived
secrets.
Enforce at the boundary
Apply controls where requests enter provider systems, gateways, or service edges.
Audit decisions, not just outcomes
Keep verifiable records of what was approved, verified, issued, denied, and why.
Install / quickstart section
Quickstart in minutes
Clone the repo, run the local stack, and send your first verified request through the demo
policy.
Community section
Built in public
Track releases, read the roadmap, open a discussion, or pick up a good-first issue. If trust is
the product, the project itself should be inspectable.24

SEO-friendly headings
For the homepage, these headings will read clearly to both humans and search engines:
Level Suggested heading

H2 Why shared API keys break down
H2 What Trustplane does
H2 Quickstart

Those headings are more search-friendly than abstract brand metaphors because they expose the product
category directly. The strongest reference pages tend to lead with the category or protocol, not with poetry. 
Short-form copy rules
Use these page-level rules consistently:
Rule Recommendation
Sentence length Prefer 10–20 words.
Paragraph length One sentence in hero, two sentences max elsewhere.
Feature cards One outcome sentence, not a mini whitepaper .
Jargon Explain “proof,” “attestation,” or “boundary” once, then use consistently.
Proof points Prefer protocol/governance/install facts over unverifiable hype.
CTA text Use verbs: Get started, Read docs, View on GitHub, Join community.

Quickstart example pattern
For trustplane.dev, the landing page should show a format , not a giant wall of config. A good pattern is:
# illustrative homepage quickstart format
gitclone<public-repo>
cd<project>
cp.env.example .env
dockercompose up
# open the local UI or send the sample request
# inspect the audit output
That works better on a landing page than a real production config because it communicates “I can try this
today” without turning the homepage into docs.
Security and privacy statement pattern
Use one plain-language block near the footer or security section:
Security and privacy
Trustplane is designed so authorization decisions can be verified, credentials can be short-
lived, and audit records can be reviewed after the fact. Security-sensitive behavior , disclosure
reporting, and version support should be documented publicly before adoption.
That kind of statement works better than a compliance badge wall on a pure OSS homepage. OSS visitors
usually want clarity of model  before they want claims of certification. This is one reason SPIFFE/SPIRE, Dex,
and Authelia feel trustworthy without sounding sales-led. 26

Contributor onboarding pattern
The contributor path should be visible from the homepage footer and from the docs nav:
Contributing
Start with the quickstart dev environment, read the architecture notes, and pick up a
beginner issue or docs task. Design discussions happen in public. Security disclosures use the
security policy, not public issues.
That mirrors what successful OSS identity projects expose: contribution guidance, public discussion, and a
separate path for vulnerabilities.

Accessibility and performance targets
Use semantic page landmarks so assistive technologies can navigate the site structure cleanly. WAI
guidance recommends landmark regions and section labeling for exactly this reason. Informative images
should have real alt text; decorative images should use null alt text. 
For visual accessibility, keep body text combinations above the WCAG minimum contrast threshold of 4.5:1 ,
and large text above 3:1. 
For performance, optimize toward “good” Core Web Vitals: LCP ≤ 2.5s , INP ≤ 200ms , and CLS ≤ 0.1  at the
75th percentile. Those are the current published thresholds. 
A practical homepage performance budget for this project is:
Budget item Target
Initial JS under 90 KB compressed if possible
Above-the-fold images under 250 KB total
Font payload 1 sans family + 1 mono family, WOFF2 only
Hero media static SVG/PNG or CSS-only illustration
Lighthouse / CWV posture design for green CWV before adding visual flourishes29

Open questions and limitations
Trustplane and Clawvisor were useful adjacent references, but their public pages in this pass did not give
me enough confidence to catalog them as verified OSS projects with publicly obvious license/repo surfaces.
Trustplane’s public docs are clear on product ideas such as request proofs, short-lived JWTs, and audit;
Clawvisor’s public site is clear on approvals, vaulting, and policy checks. But if trustplane.dev is going to ship
as a pure OSS  project, the launch page should make the repository and license unmistakable from day one. 
A second limitation is licensing clarity across some modern auth vendors. ZITADEL’s open-source page and
repo messaging are not phrased identically, and projects like Authentik, Hanko, and SuperTokens visibly mix
OSS and additional licensing layers/components. That does not make them bad references, but it does
mean they are weaker precedents for a “pure OSS” positioning than Dex, Authelia, SPIFFE/SPIRE, Kanidm,
Tinyauth, or Keycloak.
