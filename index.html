Authorization for AI agents, powered by cryptographic proof.

Give an agent an API key and you've handed it standing authority: anything that key can reach, it can be tricked into reaching. TrustPlane works differently. The problem

A long-lived token is standing authority. Hand one to an autonomous agent and a single leak, or one prompt injection, authorizes every call it can reach.

Presented, not proven

API keys and bearer tokens grant access by mere possession. Whoever holds the string is the client, from anywhere, until it's rotated.

Not bound to the request

A token that may read /orders can be pointed at /admin the moment anything slips. The credential authorizes the caller, never the call.

Invisible after the fact

Keys leak into code, logs, and prompts. Without a per-request proof there is no way to tell a legitimate call from a hijacked one.

"A token authorizes whoever is holding it. A request proof authorizes one specific call. For software that runs on its own, that difference is the whole game."
How it works

Prove the request. Don't present a secret.

TrustPlane turns a caller's existing workload identity into a short-lived, request-bound credential, verified in your own infrastructure with no external dependency per request.

01

Enroll

A caller enrolls public keys against a trust anchor. Private keys stay with the caller; TrustPlane holds only the public key and its expiry.

02

Sign

The SDK or CLI produces a canonical transcript signature over the method, path, body hash, time bucket, nonce and client identity.

03

Verify

The auth plane checks signature, request binding, session scope, replay protection and policy, then mints a short-lived downstream JWT.

04

Audit

Every allow or deny becomes an audit record tied to the exact request it decided.

Capabilities

Everything you need to authorize machine traffic.

Request binding

The proof covers method, path, body hash, time bucket, nonce and client identity. Change any one of them and verification fails closed with request_binding_mismatch.

Replay protection

Nonce storage and time-bucket validation reject the same call submitted twice, with jti_replay. Nothing is accepted outside its validity window.

Provider-owned boundary

The provider adapter verifies in front of your API, so the upstream is never rewritten. Kubernetes-compatible, never Kubernetes-required.

Short-lived downstream JWTs

After an allow, the auth plane mints a short-lived ES256 JWT for the upstream, so your backends keep verifying one familiar format.

Signed policy distribution

Compile, sign and distribute policy to every auth plane deployment, with freshness guarantees so stale policy never silently applies.

Evidence-grade audit

Every allow or deny is recorded with the proof context, the policy it matched, and the upstream result.

FAQ

The questions people actually ask.

What is TrustPlane?

TrustPlane is an open-source auth plane for AI agents and machine callers. Instead of presenting a long-lived API key or bearer token, every request carries a request proof — a canonical transcript signature over the method, path, body hash, time bucket, nonce and client identity — which is verified in the request path, recorded, and exchanged for a short-lived downstream JWT.

How is TrustPlane different from API keys and OAuth bearer tokens?

API keys and bearer tokens grant access by mere presentation, are long-lived, and can be replayed if stolen. A TrustPlane request proof is short-lived, bound to one specific request, rejected on replay, and audited per decision.

What is the difference between request binding and replay protection?

They defend against two different attacks, and it's worth keeping them apart. Request binding stops a proof being reused against a different call: change the method, path or body and verification fails with request_binding_mismatch. Replay protection stops the same call being submitted twice, using nonce storage and time-bucket validation, and fails with jti_replay.

What is the difference between the auth plane and the control plane?

The auth plane (TrustPlane Auth) verifies requests in your own infrastructure, in the request path. The control plane (TrustPlane Control) manages enrollment, compiles and signs policy, distributes it to every auth plane deployment, and handles revocation and audit.

Does TrustPlane work with SPIFFE, OIDC and MCP?

Yes. TrustPlane consumes existing workload identity from SPIFFE/SPIRE and OIDC/JWT, aligns with proof-of-possession work such as DPoP and the IETF WIMSE group, and protects MCP servers and APIs without rewriting them.

From the team

Why we built this

Secrets were never meant to be handed to software that acts on its own. An API key is a password that never sleeps: whoever holds it is you, from anywhere, until someone notices. That was a manageable risk back when a person pasted a key into a config file once a quarter.

It stops being manageable when an autonomous agent is making thousands of calls an hour and can be talked into making the wrong one. We didn't want to build another secrets manager, or another gateway with a longer config file. We wanted the request itself to carry proof, so the auth plane can decide whether each exact call is allowed, every time.

That's the whole idea. Most of what's on this site is the plumbing that makes it practical.

— The TrustPlane team
