TrustPlane Auth · the auth plane

The open-source auth plane.

TrustPlane Auth is a provider-owned boundary that runs in your infrastructure, right in the request path. It verifies a request proof on every call, decides without an external dependency per request, mints a short-lived downstream JWT, and forwards only what it can actually verify.

Request-bound proofs, not standing tokens

Each call carries a proof over that call's own parameters. Tamper with the path or resubmit the proof and verification fails closed, so a compromised or prompt-injected agent can't act beyond the single call it was authorized for.

# sign one specific call
$ trustplane sign --method GET --path /orders \
    --audience acme.orders
✓ allow   verified · downstream JWT · audited

# submit the same proof twice?
✗ deny    jti_replay
# tamper the path after signing?
✗ deny    request_binding_mismatch

A provider-owned boundary, no rewrite required

The provider adapter is a reverse proxy that verifies requests in front of your existing API, in your own infrastructure. Add a new caller by enrolling its public key, with no code change and no adapter redeploy. Kubernetes-compatible, never Kubernetes-required.

# your upstream service is unchanged
caller  →  provider adapter  →  upstream API
                │
      verify · enforce policy · audit
                │
   forwarded only when verified

Inside the auth plane

What TrustPlane Auth verifies.

Signature & identity verification
Checks the proof signature against the caller's enrolled public keys and the trust anchors you configured.
Replay protection
Nonce storage and time-bucket validation reject the same call submitted twice: jti_replay.
Request binding
Method, path, body hash and time bucket are covered by the signature; any mismatch denies with request_binding_mismatch.
Key & session state
Expired keys and out-of-scope or revoked sessions are refused before anything reaches upstream.
Policy & freshness
Enforces signed policy with freshness guarantees, so stale policy never silently applies.
Multiple trust anchors
Accept callers from several trust anchors, with per-route source rules.
Downstream JWT issuance
After an allow, mints a short-lived ES256 JWT for boundary-to-upstream forwarding or backend verification.
Evidence-grade audit
Each allow or deny is recorded with the proof context, the policy it matched, and the upstream result.
Open standards

Built on identity, not in place of it.

TrustPlane doesn't reinvent identity, and it doesn't want to replace your IdP. It consumes SPIFFE/SPIRE and OIDC/JWT, and applies the request-bound, proof-of-possession model that the IETF is standardizing through DPoP (RFC 9449), the WIMSE working group, and OAuth Transaction Tokens, pointed at the place most of us have been ignoring: AI agents and machine callers.
